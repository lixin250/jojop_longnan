# 架构模式约定（Manager / 单例 / 工厂 / 订阅）

面向 JojoP：**小团队 IAA + HybridCLR 热更**。不为「看起来企业级」上完整 DI 容器。

「末流」= 在本项目体量下容易把架构做死、以后难热更/难测的用法。

---

## 1. 总原则：组合根 + 少全局

```text
GameApp（组合根 Composition Root）
  ├─ 创建 / 持有：Ads、Api、UiPanelService、BrothersSession…
  ├─ 启动时：CfgTables.TryLoad()
  └─ 把依赖传给子模块（构造 / 字段注入）
```

| 做法 | 定案 |
|------|------|
| 每个 Manager 都 `Xxx.Instance` | **末流** |
| 一切进 Zenject/VContainer | 团队变大再议；现在 **不上** |
| 无状态查表 `CfgTables` / `RoleCatalog` | **允许 static 门面** |
| 有生命周期的会话（一局兄弟团） | **普通实例**，挂在 Session 上 |
| 跨模块通知 | **C# event / Action**；慎用全局 EventBus |

---

## 2. 单例：用哪几种、禁哪几种

### 允许（窄单例 / 静态门面）

| 类型 | 例子 | 条件 |
|------|------|------|
| **静态门面** | `CfgTables`、`RoleCatalog` | 无 Unity 生命周期；进程内一份表；可 `Unload`/`Rebuild` |
| **组合根单例感** | `GameApp` 场景里一份 | 只通过自己往下传，别人不 `GameApp.Instance` 乱抓（能免则免） |
| **渠道/设备只读** | `ChannelId`、设备 Id | 真全局常量 |

### 禁止 / 末流

| 末流 | 为什么 |
|------|--------|
| `MonoBehaviour` + `DontDestroyOnLoad` 单例丛林 | 热更域、进出会话、测试全痛 |
| Manager 互相 `Xxx.Instance.Yyy.Instance` | 隐式依赖、循环引用、无法替换 Mock |
| 「以后可能用到」先写单例 | 预支复杂度 |

**口诀：**  
- **数据表 / 纯查询** → static 门面 OK  
- **一局游戏状态** → 实例，跟着 Session 生灭  
- **系统服务（广告、UI 根）** → GameApp 创建并持有，需要时再考虑极少数 Instance  

---

## 3. 工厂：干什么用

工厂解决的是 **「怎么 new 出一堆相似对象」**，不是 Manager 替代品。

| 该用工厂 | 不该用工厂 |
|----------|------------|
| 刷怪 / 召唤 `BattleUnit` | `CfgTables`（没有多种实现要选） |
| Rogue 三选一选项生成 | 把 Session 包一层 Factory 却只 new 一次 |
| UI：`UiPanelService.Open(location)`（资源工厂） | 为每个 Panel 写巨型 AbstractFactory |

模式名可以叫 Factory / Builder，**实现上就是纯函数或小类**，别搞接口继承树。

## 4. 订阅：event 还是消息总线

| 方式 | 定案 |
|------|------|
| **模块内 / 父子** | `event Action`（已有：`WaveCleared`、`SanpangTriggered`） |
| **UI 听战斗** | Session/Battle 抛事件 → View 订阅；View **不**直接改战斗内部 |
| **全局字符串 EventBus**（`"OnKill"`） | **末流**（难搜引用、易漏退订、热更后更乱） |
| UniRx / MessagePipe | 有明确跨系统风暴再上；当前不必 |

规则：

1. 订阅方负责在 `OnDestroy` / 退出会话时 `-=`  
2. 事件载荷用明确类型，不用 `object`  
3. 不要「事件驱动一切逻辑」——状态机（`BrothersFlow`）仍是主轴  

---

## 5. 后续 Manager 怎么落位

| 模块 | 形态 | 备注 |
|------|------|------|
| `CfgTables` | static 门面 | 已定；内部可换 `ICfgRawLoader` |
| `UiPanelService` | **实例**，GameApp/UI 根持有 | 不要做成全局 Instance |
| `BrothersSessionController` | 场景实例 | 一局一生；事件给 UI |
| `SkillCastSystem` | 战斗内普通对象 | 跟 BattleController 同生灭 |
| Ads / Api | GameApp 字段 | 接口 `IAdService`，工厂只负责 Create |
| 音频 / 震动（以后） | GameApp 持有或薄 static 门面 | 优先实例，避免 Audio.Instance 点一切 |

```text
推荐依赖方向（单向）：

UI ──订阅──► Session / Battle
Session ──► CfgTables / Meta / Rogue
Battle ──► SkillCast / CfgTables
GameApp ──创建──► 以上全部
```

禁止：Battle → UI；CfgTables → Session。

---

## 6. 和「商业大作」的差距（有意不为）

| 大作常见 | JojoP |
|----------|--------|
| VContainer/Zenject 全注入 | GameApp 组合根手动接线 |
| 领域事件总线 + CQRS | `event Action` + Flow 枚举 |
| 每系统一个 Singleton Manager | 表门面 + 会话实例 |

体量上去（多玩法、多人或编辑器工具链）再引入 DI；**现在上容器是末流式过度设计**。

---

## 7. 检查清单（加 Manager 前问自己）

1. 它是 **查表** 还是 **有状态会话**？→ 决定 static 还是实例  
2. 谁 **Create**、谁 **Dispose**？→ 尽量同一层（GameApp 或 Session）  
3. 别人要不要 `Xxx.Instance`？→ 默认 **不要**；传引用  
4. 跨模块要不要解耦？→ 先 event；三个以上监听者再考虑总线  
5. 热更后能否只改 HotUpdate？→ 别把会话状态塞进 AOT 单例
